# s11：Design Tradeoffs — 比较优化目标，不比较抽象数量

> **架构没有脱离产品目标的“更先进”，只有更匹配。**
>
> Harness 层：设计决策。

[s10](../s10_composition/) → `s11` → [s12](../s12_comprehensive/)

## 问题

看到 DeepSeek Harness 的 Contract、Provider、Plugin、Scope，很容易得出“越通用越先进”；看到 Claude Code 的完整产品体验，又容易得出“集成越深越成熟”。两种结论都忽略了优化目标。

## 两种倾向

这里比较的是可观察的产品与公开设计表面，不是声称知道 Claude Code 未公开的内部实现。

| 维度 | 通用组合型倾向（DeepSeek Harness 案例） | 集成产品型倾向（Claude Code 案例） |
|---|---|---|
| 首要目标 | 支撑多实现、多入口、可嵌入 | 把编程工作流打磨成统一体验 |
| 变化处理 | 显式 Contract / Provider / Plugin | 产品内聚，公开稳定扩展面 |
| 优点 | 可替换、可组合、便于平台化 | 路径短、一致性强、产品判断集中 |
| 成本 | 抽象、装配、版本兼容、调试链更长 | 内部能力较难被第三方任意重组 |
| 适合 | SDK、平台、多租户、多产品形态 | 边界明确的成熟垂直产品 |

这不是源码行数比较。Claude Code 官方公开仓库没有公开完整核心循环源码，因此课程只比较公开可验证的产品表面和设计取舍。

## 决策实验

`code.py` 是一个很小的决策实验室。它不会替你决定架构，只会把需求转换成压力信号：

```sh
python course/s11_design_tradeoffs/code.py
```

默认案例有多入口、远端实现和第三方扩展，因此建议逐步走向组合型；把这些值全部改为 `False`，建议会回到集成型单体。

## 五个判断问题

1. 是否已经有第二种实现，而不是“未来也许有”？
2. 不同入口是否必须复用同一核心行为？
3. 第三方是否真的需要在不改核心的情况下扩展？
4. 是否需要独立部署、恢复或审计？
5. 团队是否能承担抽象协议、兼容性和调试成本？

前四个问题制造收益，第五个问题计算成本。

## 借鉴建议

- 从 Claude Code 式产品思维借鉴：强默认值、连贯体验、少让用户理解内部装配。
- 从 DeepSeek Harness 式运行时思维借鉴：事实与视图分离、能力作用域、Provider 边界、生命周期和组合根。
- 不要从任何一方借鉴“目录长什么样”；先借鉴问题分解方法。
