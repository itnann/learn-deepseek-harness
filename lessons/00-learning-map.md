# 00. 学习地图：先学会问问题，再看架构答案

> **不要从目录结构开始理解 Harness，要从它必须解决的问题开始。**

## 这套学习适合谁

你只需要具备：

- 看得懂基础 Python 或 JavaScript。
- 知道 LLM 可以返回工具调用。
- 用过命令行、文件读写或 API。

不要求提前掌握 TypeScript 高级类型、依赖注入、事件溯源或插件框架。这些名词会在真正需要时解释。

## 先建立一张问题地图

一个能完成真实工作的 Agent 产品，迟早会遇到五类问题：

| 问题 | 最小实现 | 规模变大后的难题 |
|---|---|---|
| 怎样行动 | 一个 Agent Loop + handler map | 工具越来越多，如何治理、替换、限权和并发 |
| 怎样记住 | 一个 `messages[]` | 如何恢复、压缩、分叉、回放和服务 UI |
| 怎样扩展 | 在主循环里加 `if` | 如何让新能力不污染核心循环 |
| 怎样控制风险 | 调用前写一个判断 | 审批、策略、Sandbox、取消和超时如何配合 |
| 怎样产品化 | 一个 CLI | Web、IDE、自动化、SDK 如何复用同一个核心 |

DeepSeek Harness 的意义在于：它给这五类问题提供了一套高度系统化的答案。学习重点不是记住答案的类名，而是理解答案为什么出现。

## 三层学习目标

### 第一层：看懂

能够用自己的话解释：

- Agent Loop 为什么是核心，但不应该承担所有责任。
- 为什么完整历史和模型当前看到的历史可以不同。
- 为什么 Tool 不只是一个函数。
- 为什么插件化是解决组合问题，而不是为了显得灵活。

### 第二层：会判断

看到一个需求时，能判断它应该放在哪里：

```text
改变模型看到的信息？       -> Context / Prompt / Session view
增加模型能做的事情？       -> Tool / Capability
限制一类行动？             -> Policy / Guard / Sandbox
改变能力的具体实现位置？   -> Provider
只服务 Web 或 CLI？         -> Surface adapter
需要重启后仍然存在？       -> Durable event / persistence
```

### 第三层：会借鉴

不是把 DeepSeek Harness 的包结构复制一遍，而是能选择最小足够设计：

- 小项目先保留直接函数。
- 出现第二种实现时再提取 Provider。
- 出现恢复、审计需求时再升级为事件日志。
- 出现多个 Agent 能力集合时再引入 Scope。
- 出现多个产品入口和动态组合时再考虑完整插件系统。

## 阅读顺序

```mermaid
flowchart LR
    A["模型与 Harness 的边界"] --> B["七个设计原则"]
    B --> C["DeepSeek / Claude 两种哲学"]
    C --> D["借鉴决策"]
    D --> E["渐进式构建"]
    E --> F["设计复盘"]
```

每一章都围绕四个问题：

1. 它解决什么真实问题？
2. 最简单的解决方式是什么？
3. 为什么最简单方式后来不够？
4. DeepSeek 的方案是否适合我的项目？

## 不推荐的学习方式

### 不要先记包名

知道 `agent-loop`、`session`、`tools` 的名字，不等于理解它们为什么要分开。先理解责任，再看名字只是验证。

### 不要把复杂当成熟

一个 500 行单体 Harness 可能正好满足需求；一个 50 个包的插件系统也可能只是提前设计。成熟是复杂度与问题匹配，不是抽象数量多。

### 不要把 Claude Code 当成唯一标准答案

Claude Code 是集成度很高的编程产品，DeepSeek Harness 更强调通用组合能力。二者可能都优秀，但优化目标不同。

### 不要只学“怎么加功能”

更重要的是学习不变量：哪些事实不能丢、哪些边界不能绕过、哪些生命周期必须清理。功能会变化，不变量决定系统能否长期运行。

## 每章的学习动作

读完一章，做三个小动作：

1. 用一句话复述本章设计原则。
2. 在自己的项目中找一个对应问题。
3. 写下“现在不采用这个设计”的理由，直到理由不成立再引入。

这能避免把课程变成架构名词收藏。
