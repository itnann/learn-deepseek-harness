# 04. 借鉴手册：先复制原则，再按问题提取机制

> **不要复制最终架构，要复制它解决问题的演进顺序。**

## 最重要的借鉴方法

面对一个成熟系统，最容易犯的错误是直接复制它今天的结构：monorepo、插件框架、事件总线、几十个接口和配置层。

更有效的方法是逆向它的压力：

```text
它遇到了什么问题？
原来的简单方案为什么失效？
新设计守住了什么不变量？
我的项目是否已经遇到同样压力？
```

只有第四个问题答案为“是”，才引入对应机制。

## 第一类：从第一天就值得借鉴

这些原则成本低、收益稳定，不需要等项目变大。

### 1. 明确模型与 Harness 的责任

让模型做语义判断，让代码保证权限、格式、资源和生命周期不变量。

### 2. 工具输入输出有明确协议

每个工具至少定义：

- 清晰名称和用途。
- 结构化参数。
- 成功与失败的稳定返回。
- 是否产生副作用。
- 如何响应取消。

### 3. 外部行动经过统一入口

不要让某些命令绕过工具管线偷偷执行。只有统一入口才能统一增加审计、权限和取消。

### 4. 权限与 Sandbox 分开

从一开始就区分“允许做”与“技术上最多能做”。安全边界后补通常代价很高。

### 5. 注册行为可清理

事件监听器、工具、后台任务和临时资源都应有明确 owner 和 dispose 路径。

## 第二类：出现触发信号后再引入

### Provider 抽象

触发信号：

- 出现第二种模型服务商。
- 同一工具需要本地和远程执行。
- 测试需要真正替换实现，而不仅是 monkey patch。

引入前：

```python
async def run_shell(command): ...
```

引入后：

```python
class ShellProvider:
    async def run(command, cwd, signal): ...
```

不要因为“未来可能上云”就提前提取十个 Provider。

### 事件日志

触发信号：

- 进程重启后需要准确恢复。
- UI、模型和审计需要不同历史视图。
- 需要 fork、replay 或可靠 compaction。
- 崩溃后必须判断哪些副作用可能已经发生。

引入前可以使用持久化 messages；引入后才考虑 append-only event 与 projection。

### Scope

触发信号：

- 子 Agent 不应拥有父 Agent 的全部工具。
- 不同 preset 使用不同 Prompt、模型或权限。
- 同一进程托管多个互相隔离的 Agent。

只有一个 Agent 时，显式依赖对象通常比 Scope 框架更清楚。

### 事件/中间件扩展点

触发信号：

- timeout、telemetry、approval 等逻辑开始重复包裹多个工具。
- 第三方需要扩展行为但不能修改核心。
- 功能开关不断侵入主循环。

先使用少量明确的 middleware；只有需要动态注册和作用域过滤时，再升级到 typed event system。

### 多种 Surface

触发信号：

- CLI、Web 和 SDK 都要驱动同一个 Agent。
- 某个前端开始复制业务状态或 Agent Loop。

先提取共享应用服务和事件输出；不一定立即需要完整 RPC 类型图。

## 第三类：通常只适合平台型项目

### 一切皆插件

适合：

- 运行时组合差异很大。
- 插件需要安装、卸载或热更新。
- 第三方开发者需要替换核心能力。
- 同一框架承载多个不同产品。

不适合：

- 单一应用、单一团队、单一部署。
- 组合几乎不会改变。
- 调试速度比运行时替换更重要。

### 多层 Profile / Bundle / Patch

适合需要“默认发行组合 + 团队覆盖 + 用户覆盖 + 临时 overlay”的平台。普通产品往往用一个清晰配置对象和少量环境变量更好。

### 所有子系统都做 Service seam

只有真正存在多实现、多部署或第三方扩展需求的能力值得成为 seam。稳定的内部纯函数无需被服务化。

## 按项目规模选择

| 项目阶段 | 推荐结构 | 暂时不要做 |
|---|---|---|
| 实验：1–3 个工具 | 一个 Loop、一个 handler map、简单 messages | 插件框架、事件溯源、Scope |
| 单产品：工具与策略增多 | Tool registry、统一 policy、History 接口、composition root | 所有能力动态热插拔 |
| 生产产品：需要恢复与多入口 | durable history、projection、Provider、取消、生命周期 | 无明确需求的通用平台协议 |
| 平台：多实现、多 Agent、多产品 | plugin lifecycle、Scope、profile、capability seam、RPC | 假装复杂度不存在；必须补可观察性和失败诊断 |

## 一套渐进式重构规则

### 规则一：重复出现两次，再提取变化点

只有一个实现时保留直接代码；第二个实现出现后，比较二者真正相同和不同的部分，再提取接口。

### 规则二：先把依赖显式传入，再引入容器

从：

```python
result = global_shell.run(command)
```

变成：

```python
result = shell.run(command)
```

构造时把 `shell` 传进来。只有依赖数量、动态装配和生命周期真的复杂后，再需要 Context 或 DI container。

### 规则三：先用结构化数据，再使用事件溯源

先让 Message、ToolCall、ToolResult 有稳定结构；没有稳定事件词汇，直接上 event sourcing 只会把混乱永久保存。

### 规则四：先定义不变量，再选择框架

例如工具执行系统先写下：

- 每个 call 必须有 result。
- 取消后不留下无人管理的进程。
- 被拒绝的工具 body 不能运行。
- 模型看到的结果可以被恢复。

然后再决定 handler、middleware、queue 或 event log 如何保证它们。

### 规则五：每引入一层间接性，都提供观察入口

如果实际工具由 scope、filter、profile 和 patch 共同决定，系统必须能输出“当前 Agent 最终拥有什么”。否则组合能力会变成调试黑洞。

## 值得直接采用的最小架构

对于大多数单产品 Harness，可以先停在这里：

```text
App composition root
  └─ Agent Loop
      ├─ HistoryStore
      ├─ ModelClient
      ├─ ToolRegistry
      │   └─ PolicyMiddleware[]
      ├─ ExecutionEnvironment
      └─ EventSink / UI adapter
```

它已经吸收了 DeepSeek 的主要思想：责任分离、统一工具入口、策略正交、执行环境可替换、UI 不侵入 Loop。

但它没有引入：动态插件树、复杂 Scope、profile patch、RPC 类型系统和完整事件溯源。等真实压力出现再升级。

## 常见错误借鉴

### 错误一：按 DeepSeek 的目录创建空包

包名不会自动产生边界。边界来自明确责任和依赖方向。先在一个仓库内分模块，只有独立发布或依赖治理需要时才拆 package。

### 错误二：每个函数都注册成事件

直接调用表达“我需要这项能力”；事件表达“我不知道或不拥有所有参与者”。已知的单一调用者与实现者之间，普通函数更清晰。

### 错误三：把所有配置都做成可覆盖

每个可覆盖点都扩大测试组合空间。安全不变量、协议常量和内部实现细节不应该被随意配置。

### 错误四：把日志当事件溯源

记录几行 JSON 不等于事件溯源。真正的事件日志要求事件词汇稳定、顺序可验证、状态可重建、失败边界明确。

### 错误五：插件化后忽略默认体验

平台仍需要一个直接可用的默认组合。否则使用者为了运行第一个任务就要理解所有 Service 和 Provider。

## 借鉴决策表

在引入一个 DeepSeek 机制前，填写：

```text
当前真实问题：
最小可行方案：
最小方案已经失败的证据：
需要守住的不变量：
准备引入的机制：
新增的间接性和维护成本：
如何观察和调试：
什么时候可以删除这层机制：
```

如果“最小方案已经失败的证据”写不出来，大概率还不该引入。
