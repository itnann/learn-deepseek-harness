# 06. 设计复盘清单：你的 Harness 真的需要多复杂？

> **用问题证明一层架构的必要性，而不是用架构证明项目很成熟。**

这份清单可以在设计新 Agent、重构现有 Loop 或准备平台化时使用。

## 一、先写清产品边界

```text
用户是谁：
核心任务是什么：
允许模型观察什么：
允许模型改变什么：
最坏副作用是什么：
任务持续几秒、几小时还是跨多天：
是否需要人工参与：
是否有多个前端或接入方：
```

如果这些问题没有答案，讨论插件、记忆和多 Agent 都太早。

## 二、模型与 Harness 的责任

逐项判断：

- 这个决定是否需要理解任务语义？如果是，倾向模型。
- 这个规则是否必须每次稳定成立？如果是，倾向 Harness。
- 决定错误是否会产生不可逆副作用？如果是，Harness 必须设置上限。
- 失败后是否需要模型换策略？Harness 应返回结构化、可理解的结果。

检查是否出现两个极端：

- Harness 用大量分支替模型做语义判断。
- Harness 把权限、取消和一致性也交给模型自觉遵守。

## 三、Agent Loop

- Loop 是否只负责模型请求、工具结果和继续/停止？
- 新功能是否不断给 Loop 增加 `if feature_enabled`？
- Turn、Step 和一次工具执行是否有清楚含义？
- 用户中途追加消息时，系统知道它属于当前 Step、下个 Step 还是下个 Turn 吗？
- Loop 发生异常时，是否仍能留下可解释的结束状态？

警报信号：Loop 同时导入数据库、WebSocket、权限 UI、文件系统和所有工具实现。

## 四、工具与行动

为每个工具填写：

```text
名称与用途：
结构化输入：
成功返回：
失败返回：
副作用：
是否可以安全重试：
是否可以与兄弟调用并发：
如何取消：
需要什么权限：
在哪个执行环境运行：
```

再检查：

- 所有行动是否经过统一 Tool Runtime？
- 参数验证、Policy、Approval 和 Sandbox 是否分开？
- 工具失败是否返回模型能纠正的结果，而不是只写服务器日志？
- 并发是否由明确安全承诺决定，而不是简单按工具名猜测？
- 每个 tool call 是否最终都有 result，包括拒绝和取消？

## 五、历史与上下文

- 用户实际经历的 transcript 与模型当前上下文是否需要不同？
- 压缩会不会破坏审计和恢复？
- 系统重启后能否知道最后一个工具是否已经开始执行？
- Prompt、工具 schema 和注入上下文是否能解释“模型当时为什么这样回答”？
- 是否真的需要事件日志，还是一个持久化 MessageStore 已经足够？

引入事件日志前必须回答：

```text
事件的稳定词汇是什么？
顺序如何保证？
哪些状态可以由事件重建？
半完成操作怎样表达？
格式升级怎样处理？
```

答不出来时，事件日志可能只是换了名字的调试日志。

## 六、能力与 Provider

对准备抽象的能力提问：

- 已经存在几种实现？
- Consumer 真正依赖的最小能力是什么？
- Provider 之间是否共享一致语义？
- 切换 Provider 时，模型工具是否应该保持不变？
- 多项能力是否必须属于同一个 execution world？

只有一个实现且没有测试替换需求时，优先使用直接依赖。

## 七、权限与安全

分别填写三层：

| 层 | 当前设计 |
|---|---|
| Policy：按规则能否尝试 |  |
| Approval：谁能授权一次行动 |  |
| Sandbox：技术上最多能访问什么 |  |

检查：

- 用户批准能否意外突破 Sandbox？答案必须是否。
- 模型能否通过另一条未治理入口达到同样副作用？
- 子 Agent 是否继承了超出任务所需的能力？
- 网络、凭据、文件和进程是否分别有最小权限？
- 拒绝结果是否会返回模型，帮助它选择安全替代方案？

## 八、生命周期与取消

列出所有可能长于一次函数调用的资源：

- 子进程。
- 网络流。
- 浏览器或终端会话。
- 后台任务。
- 子 Agent。
- 文件监听器和事件订阅。
- 数据库事务或锁。

为每种资源回答：谁创建、谁取消、谁等待结束、谁最终清理？

如果答案是“进程退出会自动清理”，生产环境通常还没有设计完成。

## 九、Scope 与多 Agent

- 不同 Agent 是否真的拥有不同能力集合？
- 能力是显式授予，还是从全局环境偶然继承？
- 父 Agent 能否观察和取消子 Agent？
- 子 Agent 结果怎样进入父 Agent 上下文？
- 子 Agent 的权限审批路由到哪里？
- Scope 只控制可见性，还是被错误地当成 Sandbox？

只有角色差异，没有动态嵌套时，几个显式配置对象可能比通用 Scope 树更清楚。

## 十、组合与产品入口

- CLI、Web、IDE、SDK 是否共享同一个 Agent 核心？
- 产品差异集中在 composition root，还是散落在各模块的模式分支？
- 用户是否需要动态安装/卸载能力？
- 最终运行配置能否被打印和解释？
- 配置错误是在启动时失败，还是运行到深处才静默缺功能？

如果组合不会在运行时变化，普通构造代码优于插件 Loader。

## 十一、复杂度账单

每引入一种机制，都填写收益和成本：

| 机制 | 解决的真实问题 | 新增成本 | 如何调试 | 删除条件 |
|---|---|---|---|---|
| Provider |  |  |  |  |
| Event log |  |  |  |  |

| Plugin system |  |  |  |  |
| Profile/Patch |  |  |  |  |

“更灵活”不是充分收益，必须写清谁在什么场景真正需要替换什么。

## 十二、一个完整示例：代码审查 Agent

### 需求

- 读取代码和 Git diff。
- 运行只读搜索。
- 生成审查意见。
- 不允许修改文件。
- Web 和 CI 都能调用。
- 任务最长五分钟，无需跨天恢复。

### 合理设计

```text
Shared Agent Service
  ├─ 简单持久化 MessageStore
  ├─ Tool Registry: read / grep / git_diff
  ├─ ReadOnly Policy
  ├─ ReadOnly Container Environment
  └─ Cancel token + timeout

Adapters
  ├─ Web API
  └─ CI command
```

### 暂时不需要

- 完整事件溯源：任务短，MessageStore 足够恢复基本失败。
- 动态插件系统：工具集合由单一团队维护。
- 通用 Scope：只有一种只读 Agent。
- Profile/Patch：两个入口共享同一能力，只需不同 Adapter。

### 未来触发升级

- 加入能修复代码的 Agent：引入不同 Scope 和审批策略。
- 运行在本地与云端：抽象 ExecutionEnvironment Provider。
- 需要完整回放和 fork：升级为事件日志与投影。
- 允许第三方工具：增加插件生命周期与最终配置检查。

这就是“借鉴设计思想”的核心：不是今天复制最终形态，而是知道未来压力出现时该向哪里演进。

## 三十分钟设计练习

选择你自己的一个 Agent 想法，完成：

1. 五分钟写产品边界。
2. 五分钟列出所有外部副作用。
3. 五分钟画最小 Loop 与三个依赖。
4. 五分钟选择当前停止阶段。
5. 五分钟列出两个未来升级触发条件。
6. 五分钟删除一个目前没有证据支持的抽象。

## 最终检查

一个健康的 Harness 设计应当满足：

- 模型拥有判断空间，但不能绕过系统边界。
- 核心循环容易解释。
- 每项外部行动有统一入口和明确后果。
- 历史复杂度与恢复需求匹配。
- 抽象来自真实变化，不来自想象中的未来。
- 资源有 owner，取消有路径，失败有记录。
- 默认组合可以直接工作。
- 读者能说明为什么系统现在停在这个复杂度层级。

如果这些都成立，就已经学到了 DeepSeek Harness 最值得借鉴的部分，即使你的项目最终只有几百行代码。
