# 03. DeepSeek Harness 与 Claude Code：两种值得学习的产品哲学

> **比较架构前，先比较它们想优化什么。**

## 比较边界

DeepSeek Harness 的核心源码公开，因此可以讨论它明确声明的内部设计。Claude Code 当前官方公开仓库主要展示产品、插件、Hook、Agent、Skill 和配置表面，不包含完整核心运行时源码。

所以本章比较的是可观察的设计哲学，不会声称 Claude Code 内部一定使用某种类、状态机或数据结构。

## 一句话区别

```text
Claude Code：优先提供一个高度集成、观点明确的编程 Agent 产品

DeepSeek Harness：优先提供一个能力可以替换、组合和多入口复用的 Harness 平台
```

这不是“产品 vs 开源”的简单区别，而是优化目标不同。

## 两种中心

### Claude Code：体验中心

从公开产品表面可以看到，它围绕编程工作流提供统一体验：终端、IDE、GitHub、权限、Hooks、Plugins、Skills、Agents 和 Agent SDK 都服务于 Claude Code 这一个明确产品身份。

这种路线的优势：

- 默认体验一致，用户不需要理解底层装配。
- 能围绕编程任务做深入、连贯的产品优化。
- 工具、权限、交互和模型可以共同演进。
- 文档和生态围绕稳定的用户概念组织。

潜在取舍：

- 用户主要在产品提供的扩展面上扩展。
- 核心内部替换能力从公开材料中不可见。
- 想把它重组成完全不同的产品，通常需要 SDK、Plugin 或外部集成，而不是重新装配其内部核心。

### DeepSeek Harness：组合中心

DeepSeek Harness 把模型适配、Session、Agent Loop、Tools、Sandbox、Subagent 和产品入口都视为可装配插件。Web 与 headless 不是两个分叉版本，而是同一核心的不同组合。

这种路线的优势：

- 能替换模型、Provider、执行环境和前端。
- 适合研究不同 Harness 设计或托管多种 Agent 后端。
- 新能力可以通过 Service 和 Event 接入，而不必修改核心循环。
- 同一进程可以组合不同 Agent preset 和能力集合。

潜在取舍：

- 学习和调试门槛更高。
- 实际行为同时由源码、配置和插件生命周期决定。
- 抽象数量多，小团队容易把精力花在框架而不是产品上。
- 高度可替换会增加不兼容组合和失败诊断的压力。

## 六个设计维度

| 维度 | Claude Code 可观察哲学 | DeepSeek Harness 明确哲学 | 可借鉴的判断 |
|---|---|---|---|
| 主要目标 | 做好一个编程 Agent 产品 | 构造可组合 Harness 平台 | 先明确自己做产品还是基础设施 |
| 默认体验 | 集成、观点明确 | 由 profile/bundle 组合 | 终端用户更需要好默认值，平台用户更需要替换点 |
| 扩展方式 | Plugin、Hook、Skill、Agent、MCP、SDK | Service、Provider、Consumer、typed event、patch | 对外扩展面不必等于内部模块边界 |
| 产品入口 | 终端、IDE、GitHub 等统一品牌表面 | Web、headless、ACP、SDK 等组合表面 | 多入口应复用核心，但不一定需要动态插件树 |
| 安全控制 | 公开 settings、permission、Hook、Bash sandbox | policy、approval、sandbox、provider 分层 | 两者都提示我们：授权与隔离应分开 |
| 可学习性 | 产品概念清晰，内部实现不公开 | 内部设计完整公开，但概念密度高 | 学产品交互看 Claude，学通用架构看 DeepSeek |

## 不要把“可扩展”混成一种东西

至少有三种扩展：

### 1. 内容扩展

增加 Prompt、Skill、规则和领域知识。

这是最轻量的扩展。多数团队先需要这一层，不需要改运行时。

### 2. 能力扩展

增加 Tool、MCP、API 或特殊 Agent。

这需要明确输入输出、权限和错误语义，但仍可以依附在稳定产品核心上。

### 3. 架构扩展

替换 Session、Agent Loop、模型 Provider、Sandbox 或整个产品入口。

这是 DeepSeek Harness 特别强调的层级，也是成本最高的一层。只有平台、研究框架或多部署环境真正需要它。

Claude Code 的公开插件生态覆盖前两层很强；DeepSeek Harness 则把第三层也设计成一等能力。它们不是简单的“插件多”和“插件少”。

## learn-claude-code 在中间扮演什么角色

`learn-claude-code` 不是第三种生产架构，而是一种优秀的教学方法：

```text
s01 一个循环
s02 加工具分发
s03 加权限
s04 加 Hook
...
s20 合成完整 Harness
```

它告诉我们一个重要学习原则：**每次只引入一种新责任，并说明它相对上一阶段解决了什么。**

本项目借鉴的是这种教学节奏，再用 DeepSeek Harness 展示同一责任进入平台化后会怎样演进。

## 哪一种更值得借鉴

### 如果你在做一个明确产品

优先学习 Claude Code 可观察的产品哲学：

- 好默认值比无限配置更重要。
- 扩展面围绕用户任务组织，而不是暴露所有内部模块。
- Prompt、工具、权限和交互需要共同设计。
- 用户不应该先理解框架才能完成工作。

然后选择性借鉴 DeepSeek：

- 把外部副作用与策略分开。
- 把历史事实与模型视图分开。
- 让多个入口复用同一核心。
- 为未来可能替换的执行环境保留干净接口。

### 如果你在做平台、SDK 或研究框架

更值得学习 DeepSeek：

- 能力接口、Provider 和 Consumer 的分层。
- 组合根和插件生命周期。
- 作用域化工具与 Prompt。
- 事件日志、重放与多种投影。
- 用 fail-loud 配置控制复杂组合。

同时学习 Claude Code 的克制：平台最终仍要给用户提供完整、连贯的默认体验，不能把所有装配成本推给使用者。

## 一个重要反例：不要同时追求两个极端

最危险的架构是：

- 内部像平台一样复杂；
- 对外又没有稳定扩展协议；
- 默认体验还需要用户手工装配。

这样既没有集成产品的易用性，也没有平台架构的可替换性。

做设计时必须明确“复杂度由谁承担”：

```text
集成产品：开发团队承担复杂度，用户获得一致体验
组合平台：框架承担生命周期和协议复杂度，开发者获得替换能力
简单项目：暂不承担这些复杂度，直接解决当前任务
```

## 思考练习

为下面三个项目选择更接近哪种哲学，并说明理由：

1. 公司内部的代码审查助手，只支持一个模型和 GitHub。
2. 需要比较五种模型、三种 Sandbox 的 Agent 研究平台。
3. 面向普通用户的本地文件整理应用。

参考思路：1 和 3 更需要集成、观点明确的产品；2 更需要可替换、可观察的组合平台。即使选择平台哲学，也应先提供一个能直接运行的默认组合。
